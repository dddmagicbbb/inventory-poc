# Workflow — 구현 · 검증 루프와 Git 규칙

> 작성일: 2026-11-25
> 이 문서가 **Issue 하나를 받아 끝낼 때까지의 절차**와 **Git · 협업 규칙**의 원본이다. 원본 지정의 근거는 [`SSOT.md`](SSOT.md) §1이다.
> 검증 명령과 단계는 [`Verification.md`](Verification.md), 충돌 처리는 [`SSOT.md`](SSOT.md) §7, 변경 권한은 §8이 원본이다. 여기서는 순서만 정하고 그 내용을 다시 적지 않는다.

---

## 0. 원칙

1. **Issue만 읽으면 이어갈 수 있어야 한다.** 세션 · 에이전트 · 기기가 바뀌어도 Issue 본문과 코멘트에 모든 상태가 있어야 한다.
2. **대화에만 남은 결정은 없는 것으로 본다.** 사람의 결정, AI가 내린 판단, 남은 질문은 [3절 작업 기록](#3-작업-기록-코멘트)으로 Issue에 남긴다.
3. 한 Issue = 한 브랜치. 다른 Issue나 하네스 변경을 섞지 않는다.

## 1. 단계

| # | 단계 | 할 일 | 통과 조건 |
|---|---|---|---|
| 1 | **읽기** | `gh issue view <번호> --repo dddmagicbbb/inventory-poc --comments` — 본문과 **가장 최근 작업 기록 코멘트**를 읽는다 | 종료 조건 · 기계 검증 · 경계 · 루프 한도를 확인했다 |
| 2 | **막힘 확인** | `NEEDS_HUMAN` 라벨이 있으면 멈추고 사람에게 묻는다. 해제 절차는 [SSOT §7](SSOT.md#7-충돌-정책) | 라벨이 없거나, 해제 코멘트가 있다 |
| 3 | **시작 점검** | ① `git status`가 깨끗한가 — 아니면 **그 변경을 들고 가지 않고** 사람에게 묻는다 ② `git fetch` 후 `main` 최신에서 시작 ③ 이 Issue의 브랜치가 이미 있으면(로컬 · `origin`) 새로 만들지 않고 이어간다 ④ 담당자 확인 — 다른 사람 · 세션이 잡고 있으면 멈추고 묻는다 ⑤ 같은 원본 절을 건드리는 다른 Issue가 진행 중이면 순서를 사람에게 묻는다 | 깨끗한 작업 트리 · 겹치는 작업 없음 |
| 4 | **착수 표시** | `gh issue edit <번호> --add-assignee @me` · 작업 기록 코멘트(상태 `착수`)를 남긴다 | Issue에 담당자 · 브랜치 이름이 보인다 |
| 5 | **구현** | Issue 범위 안에서 고친다. 종료 조건 테스트를 함께 만든다 ([Verification §2-1](Verification.md#2-1-issue-종료-조건-테스트)) | — |
| 6 | **검증** | `npm run verify`. **한 번 실행 = 루프 1회.** 실패해서 고치고 다시 돌리면 +1 | 종료 코드 0 |
| 7 | **화면 확인** | 화면(`src/app` · `src/components`)을 바꿨으면 [4절](#4-화면-확인)대로 확인한다 | 확인 결과 또는 "미확인"이 작업 기록에 있다 |
| 8 | **커밋 · push** | [2절](#2-git-규칙) 형식으로 커밋하고 바로 push | `origin`에 브랜치가 있다 |
| 9 | **보고** | 작업 기록 코멘트(상태 `검증 통과`)를 남기고, 같은 내용을 사람에게 보고한다 | 종료 조건 ↔ `it()` 대응표가 있다 |
| 10 | **머지 · 닫기** | **사람이 승인했을 때만.** [2절](#2-git-규칙) 머지 절차 → `gh issue close <번호> --comment "<머지 커밋>"` | Issue 닫힘 · 브랜치 삭제 |

### 루프 한도
- Issue §6 "구현 루프 최대 횟수"는 6단계 실행 횟수다. **세션이 바뀌어도 이어서 센다** — 작업 기록의 `루프` 값에서 시작한다.
- 한도에 닿았는데 통과하지 못했으면 멈춘다. 작업 기록 상태를 `한도 초과`로 남기고 실패한 단계 · 오류 위치를 사람에게 보고한다.
- 문서만 바꾼 작업은 6단계를 건너뛸 수 있다 ([AGENTS.md](../../AGENTS.md) 1-1). 건너뛰면 작업 기록에 그렇게 적는다.

### AI가 판단해도 되는 것
- Issue와 원본(01 · 06)으로 답이 정해지는 것만 그대로 따른다.
- 둘 다 답하지 않는 판단(예: 이 규칙을 어느 화면까지 적용할지)은 AI가 **임시로** 정할 수 있다. 단, 작업 기록의 `결정`에 **`AI 임시`** 로 표시하고, 보고할 때 사람에게 확인을 요청한다. 사람이 확인하면 `사람 확정`으로 바꾼다.
- 원본과 어긋나는 판단은 임시로도 내리지 않는다 — [SSOT §7](SSOT.md#7-충돌-정책) `NEEDS_HUMAN`.

### 범위 밖에서 발견한 것
- 고치지 않는다. 작업 기록의 `후속`에 적고 사람에게 알린다.
- 새 Issue가 필요하면 **사람에게 묻고** 양식(`.github/ISSUE_TEMPLATE/maintenance.yml`)으로 만든다. 만든 뒤 번호를 `후속`에 적는다.

## 2. Git 규칙

| 항목 | 규칙 |
|---|---|
| 시작점 | 최신 `main` |
| 브랜치 | `<종류>/issue-<번호>-<기능명>` — 기능명은 종료 조건 테스트 파일명과 같게 (예: `fix/issue-2-fefo-expired-lots`) · Issue가 없는 하네스 · 문서 작업은 `docs/<주제>` · `chore/<주제>` |
| 종류 | `fix` 결함 · `feat` 기능 · `refactor` 동작 불변 정리 · `test` 테스트만 · `docs` 문서만 · `chore` 설정 · 도구 · `ci` 워크플로 |
| 커밋 제목 | `<종류>: <한국어 요약> (#번호)` — 한 줄 |
| 커밋 본문 | 무엇을 왜 바꿨는지 목록 · 보호 영역을 바꿨으면 `승인: <누가> <날짜> <무엇>` 한 줄 · 마지막에 `Refs #번호` |
| 커밋 단위 | 원본(01 · 06) 변경과 코드 변경은 **커밋을 나눈다** (`docs:` 커밋을 먼저). 같은 브랜치여도 된다 |
| 커밋 시점 | `npm run verify` 종료 코드 0 다음 (문서만 바꾼 경우 제외) |
| push | 커밋하면 바로 push. 새 브랜치는 `git push -u origin <브랜치>` |
| 금지 | `--force` push · `--no-verify` · 남의 미커밋 변경을 함께 커밋 |
| PR | 기본은 만들지 않는다. 사람이 요청하면 만든다 (CI가 PR에서도 돈다) |
| 머지 | **사람의 승인이 있을 때만.** `main`에서 `git merge --no-ff <브랜치>` → `git push origin main` |
| 머지 후 | 머지 · push가 성공하면 묻지 않고 브랜치를 지운다 — `git branch -d <브랜치>` · `git push origin --delete <브랜치>`. 실패하면 지우지 않는다 |

## 3. 작업 기록 코멘트

Issue 진행 상태를 남기는 유일한 곳이다. **단계 4 · 6(회차마다) · 9 · 10, 그리고 세션을 끝내기 전**에 새 코멘트로 남긴다. 다음 세션은 **가장 최근 것**을 따른다.

```markdown
<!-- work-log -->
## 작업 기록 — #<번호>

- 상태: 착수 | 진행 | 검증 통과 | 한도 초과 | NEEDS_HUMAN | 완료
- 브랜치: `<브랜치>` · 마지막 커밋 `<해시>`
- 루프: <실행 횟수> / <한도> · 마지막 verify: 종료 코드 <0|n> (<실패 단계>)

### 결정
- <내용> — 근거: <원본 절 | 사람 결정 날짜> — `사람 확정` | `AI 임시`

### 남은 질문
- <사람이 정해야 할 것>

### 종료 조건 대응
| 종료 조건 | 테스트 `it()` | 결과 |
|---|---|---|

### 원본 · 보호 영역 변경
- <파일 §절> — 승인: <누가 · 날짜>

### 확인하지 못한 것
- <화면 미확인 등>

### 후속
- <범위 밖 발견 · 새 Issue 번호>
```

- 비어 있는 절은 `없음`으로 적는다 (지우지 않는다 — 다음 세션이 "확인했는데 없음"과 "안 적음"을 구분할 수 있게).

## 4. 화면 확인

`npm run verify`는 화면을 확인하지 않는다 ([Verification §5](Verification.md#5-아직-검증하지-않는-것)). 화면을 바꿨으면 아래 중 하나를 한다.

1. **Issue 재현 절차를 다시 돌린다** — `npm run dev` 후 Playwright(모바일 폭 400×860, 계정 `warehouse@demo.kr`)로 Issue 1번 배경의 절차를 그대로 해 보고, 바뀐 결과를 작업 기록 `종료 조건 대응`이나 `확인하지 못한 것`에 적는다. 스크린샷은 `docs/screenshots/issues/`에 `<Issue 번호>-<설명>-after.png`로 둔다.
2. 돌릴 수 없으면 **"화면 미확인"** 을 `확인하지 못한 것`에 적고 사람에게 확인을 요청한다.

개발 DB(`prisma/dev.db`)는 시드 데이터다. 확인하다 바뀐 데이터는 `npm run seed:reset`으로 되돌린다.
